## Pass 5 — Regression hunt (2026-05-22, same day)

You asked the right question: "did you test for functionality?" The honest
answer was no, and the synthetic-session walkthrough that followed turned
up TWO regressions introduced by the audit itself.

### Regression A — planners couldn't save edits

`Migration 028` dropped the stale `"Supports planners can update assigned
clients"` TO-public policy, assuming `managers_and_supervisors_write_clients`
from migration 016 covered planner writes. It does not — that policy
explicitly excludes supports_planner. Every save in `ClientEditForm.tsx`
(line 550) by a planner would have failed silently with an RLS error.

Fix: **Migration 033** adds back `supports_planner_update_assigned_clients`
scoped to `assigned_to = auth.uid()` (WITH CHECK pins it both sides so a
planner can't reassign-and-escape via the same path).

### Regression B — infinite RLS recursion on profiles

The `elevated_can_view_all_profiles` policy added in migration 028 did
`EXISTS (SELECT 1 FROM profiles me WHERE me.id = auth.uid() AND me.role IN (...))`.
The inner subquery is itself subject to RLS on profiles, so Postgres
ended up in a cycle: every query against profiles errored with
`"infinite recursion detected in policy for relation 'profiles'"`.

This wasn't theoretical — it broke profiles SELECTs (browser-side
`ClientEditForm.tsx` joins notes/activity to `profiles(full_name)`) and
propagated to any policy that did `EXISTS (SELECT FROM profiles WHERE…)`,
which is half the RLS surface I added or rewrote in this audit.

Fix: **Migration 034** introduces `public.current_user_role()`, a
SECURITY DEFINER helper owned by postgres (BYPASSRLS), and rewrites every
recursive policy to call it instead of doing an `EXISTS profiles` subquery.
Covers profiles, clients (all four policies — three from 016, one from
033), client_notes, activity_log, client_documents.

### Synthetic verification

Tested by issuing `SET LOCAL request.jwt.claims = '{"sub":"…","role":"authenticated"}'`
inside a transaction and running real INSERT/UPDATE/SELECT statements
against the live tables (rolled back afterwards).

| Role | Operation | Result |
|------|-----------|--------|
| Active planner | SELECT own profile | ✅ allowed |
| Active planner | SELECT assigned client | ✅ allowed |
| Active planner | INSERT note on assigned client | ✅ allowed |
| Active planner | INSERT activity_log on assigned client | ✅ allowed |
| Active planner | UPDATE assigned client | ✅ allowed |
| Active planner | SELECT *unassigned* client | ✅ denied (count=0) |
| Active planner | INSERT note on *unassigned* client | ✅ denied (RLS check_violation) |
| Active planner | INSERT note with forged `author_id` | ✅ denied (RLS check_violation) |
| Active supervisor | SELECT all clients / profiles / notes / activity | ✅ allowed |
| Active supervisor | UPDATE any client | ✅ allowed |
| Disabled user (raw_user_meta_data.disabled=true) | any operation | ✅ denied (RESTRICTIVE `is_active_user()`) |

### Lesson

The pattern that bit me: when replacing a stale RLS policy that uses
`EXISTS profiles` as the role check, the replacement (whether that's a
removed policy with a still-valid replacement or a new policy meant to
be tighter) needs to be verified by **actually executing** a representative
query under the relevant role's JWT context. `tsc --noEmit` and advisor
scans miss this entire class of issue.
